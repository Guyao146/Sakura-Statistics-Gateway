# 指标口径

所有统计以 `STATISTICS_TIMEZONE` 的自然日归属，默认 `Asia/Shanghai`。客户端上报 UTC 时间，服务端按时区生成事件日。部署后不要随意改统计时区：已有存储日不会自动重算，v0.2.0 新增的 rebuild 也只按指定范围重算现存聚合，不能当作时区迁移工具。

| 字段 | 当前计算方式 |
| --- | --- |
| `active` | 每应用在所选区间出现过任意有效事件的去重 `anonymous_id` 数；每日序列为当天去重数 |
| `starts` | desktop 的有效且未重复 `app_start` 条数 |
| `sessions` | web 的 `session_id` 数，按该 session 最早事件所在日归属；desktop 不计此字段 |
| `page_views` | web 的有效且未重复 `page_view` 条数 |
| `custom_events` | 每应用每个统计日有效 `custom` 事件条数；不同 `event_id` 的同名事件各计一次，服务端不合并 |
| `new_visitors` | 该应用 `anonymous_id` 最早事件日在查询范围内的人数 |
| `versions[].active` | 所选区间该版本/platform 组合出现事件的去重匿名 ID 数 |
| `versions[].starts` | 该版本/platform 的启动条数 |
| `pages[].page_views` | 去除 query/fragment 后按路径分组的 page_view 条数 |
| `last_event_at` | 应用已接收事件的最大 occurred_at，迟到的旧事件不会把时间往回推 |

`active` 当前包含启动、页面访问和自定义事件。显式 `active` 是补充真实交互的事件，后台周期定时器不能代表用户活跃。区间去重活跃数不是每日活跃数之和。总览按应用分别去重后求和，同一个人使用两个应用会计为两个应用访客，不做跨端身份合并。

新增访客以**已知最早事件日**为准，补报更早事件可能将其归属移动到更早一天。Web session 同样按最早事件日归属；跨午夜保持同一 session 不会在第二天产生新 session 计数，但第二天的活跃/页面访问仍正常计数。服务端没有隐式 30 分钟 session 超时逻辑；随附网页 SDK 会在 30 分钟无事件后自行生成新的 session ID。版本分布各行可能重复同一个访客，因此行数相加可以大于整体活跃数。

Python 示例每进程创建一个 session ID，每个状态目录/应用每进程最多自动记录一次 app_start；`mark_active()` 在真实使用时由调用方触发，同一统计日 5 分钟内合并，跨统计日的首次交互即使相隔不到 5 分钟也记录。没有交互就没有新的 active 心跳。

`custom` 事件目前仅桌面/HTTP 接入支持：Python 示例通过 `track_custom(name)` 发送，其他客户端可按协议直接构造。**网页 SDK 尚无发送自定义事件的接口**，不要把 `custom_events` 的增长归因于网页接入，也不要期待网页 SDK 提供等价方法。事件名为客户端自报字符串，只做计数，不能证明对应业务动作真实发生。

事件 ID 去重只能避免同一个事件在网络重试时被重复累计。清除客户端状态、更换安装目录、复制状态目录、客户端时钟错误和恶意构造事件都会影响数字。第一版没有设备证明、实名身份、跨端匹配、反作弊评分或真实性认证。请明确向接入方说明采集目的，并避免采集不必要的身份信息。

## 周留存

`GET /api/apps/{id}/retention?weeks=N`（`weeks` 须为 1–12）按 ISO 周（周一起始）分桶，每行包含：

- `cohort`：访客（应用内去重 `anonymous_id`）首次出现所在的 ISO 周。
- `size`：该周首次出现的去重访客数。
- `retained[0]`：首访周内产生有效事件的访客数。
- `retained[1]` 及后续元素：首访周后第 1、2……周仍有任意有效事件（含 `custom`）的去重访客数。

接口同时返回服务端统计时区 `timezone` 和统计日 `today`。尚未开始的周不应当作零留存；当前周的数据尚未完整，后台会标注「进行中」。

留存按周去重：区间内整体去重活跃数不等于各周数字相加。同一访客可计入首访周及多个回访周，但同应用的一个匿名标识仅归属于一个首访 cohort。补报更早事件可能把访客的首次出现周移动到更早的 cohort，与新增访客的归属规则一致。

## 采集计数

`GET /api/metrics?from=YYYY-MM-DD&to=YYYY-MM-DD` 返回每个应用的 `requests`、`accepted`、`duplicates`、`rejected`、`rate_limited`，以及合计与按日序列：

- `requests` 是应用被识别之后的采集请求数；应用不存在导致的 404 不计入、也不记录。
- `accepted`、`duplicates`、`rejected` 与采集响应的同名字段口径一致；`rate_limited` 是被限流拒绝的请求数。

计数来自 `operation_metrics` 表，按应用按日记录，用于容量与接入健康度观察；它只反映请求与校验结果，不能证明事件真实性。

## 保留与重建

默认 `RETENTION_DAYS=0`，原始事件与聚合持续保留。启用保留期（至少 7 天）后，后台仅分批删除超出窗口的原始事件行，聚合与去重表不清理：汇总指标、累计新增与去重记录保留历史，而版本/页面/自定义事件明细和 rebuild 的可重算范围只覆盖保留窗口。v0.2.0 提供 `POST /api/apps/{id}/rebuild` 按现存原始事件重算指定范围聚合；跨时区迁移和数据库降级仍需专门实现，不能仅改配置或删除表完成。
